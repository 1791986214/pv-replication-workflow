# 本次 PV 项目复盘

用户提前提供了“关键画面重绘 → Python 逐帧合成 → FFmpeg 编码”的经验，以及缺姿态、颜色判断和遮罩导致返工的警示。后续仍多次出现相同类型问题，说明本次执行没有把这些经验落实为生成前和交付前的检查条件。责任在生产与审查流程，不应归因于用户需求多、模型天生会犯错或子智能体未理解。

本稿合并本次对话、R3 修复/合片记录与另一制作会话的实际报告 `docs/retrospective-peer-v11.md`。对方核对了 V7–V11 的实现、交付哈希、112 张采用 patch 和相关 V8 冻结块，但没有重审全片或重编码。用户发现的所有历史问题并非都有可量化诊断日志；对仅有用户观感而缺少中间产物的问题，下表区分症状与可以确认的根因，不补造统计。

## 反复返工的路径

| 用户指出的症状 | 过程中的缺口/证据 | 下一次要改变的决策 |
| --- | --- | --- |
| 多处没有头发摇曳、手部动作、吹气/开眼，甚至整镜头静态 | 源动作拆分不够详细，代表帧与整体平移代替了局部差分；生成数量不能说明覆盖 | 生图前按物体建立姿态/表情/局部相位合同，生成后从源事件与采用 cel 双向核对 |
| 吹气两次或生成图放错帧，左右眼神反了 | 状态事件和源连续帧没有一一对应，改画之前没有先锁定相位 | 先回看整个动作；头后倾、向前、吹、收势分帧，不用固定循环猜相位 |
| 鞋脚像同一只脚、膝盖与鞋方向冲突、腿长/服饰不一致、裙子身体错位 | 服装/人体几何在多次生成中漂移；不合格图注册进了合成 | 以批准设定锁定左右服饰、身高比例和鞋面透视，完成完整人体审查再进场景 |
| 修一帧眼神后画风改变，嘴/脸线歪，两眼不协调 | 本地 R3 整头修复记录确认此前局部 owner 接缝、旧眼嘴/下巴残留和领口连接有问题 | 用完整同构图 head owner，共享注册参数，完整清旧 owner，放大所有差分与编码可见帧检查 |
| 兔子提前遮帽/重复、持帽头上还戴帽、动物身体缺失、拥抱手臂被遮掉 | 道具/人物同一区域有多个来源或遮罩范围/层序不合实际接触；各历史帧根因不全有日志 | 语义实例唯一 owner，接触点/前指/帽兔前后层逐事件写清并逐帧核对 |
| 魔女恢复突然、烟团裁在遮罩内、魔女阶段却笑 | 正常/魔女单开关不能表达互救剧情，特效没有完全遮盖换装，状态原画不匹配 | 六个剧情状态分别配置；特效完整画布，第三密集 cel 内换形态；变前变后表情单独作画 |
| 最新静态图通过但交付 MP4 仍有问题 | 静态审查、编码与实际播放未形成同一输出哈希闭环；曾有浏览器权限阻碍 | 记录实际 MP4 的原速/半速播放及范围；权限未解决就保持“未播放”，不写自评通过 |
| 工作区越来越大、局部修订耗时多 | 多轮全片缓存、预览与重复包累积；渲染、诊断与编码粒度过大 | 资产依赖键、区间 patch、关键证据与清理 dry run；先保留闭包，再删可重建与确实重复的文件 |

“黄色就是蝴蝶”和“最大的连通区域就是框”的风险在上游经验中已写明，却仍需要后期纠偏。原因不是缺一条提醒，而是提醒未进入实际 owner、追踪失败条件和验收产物。把警示换个措辞再总结不能解决这个问题；应让代码消费同一合同，缺来源、缺姿态或缺证据时停止生产。

## 效率与协作的诚实边界

没有完整工时、token、生成采用率日志，无法给出“流程提升了几倍”的可信数字。可以确认的是最后阶段只重做 77 帧，并用已有完整 MP4 完成合片；这一粒度比重新合成全部图层更适合局部返修。

多会话协作应先冻结最新文件哈希、镜头区间和文件所有权。讨论需要产出能改变下一次执行的合同或代码检查，不只是相互肯定结论。合并者负责核对两个交付版本、对方已批准选择以及两个切镜边界。重复抽帧和清单适合并行；源动作理解、人体审查和最终验收仍要有人明确承担。

## 另一会话核对后，确认的执行问题

已有 V7/V8 package/export 会核对视觉记录、当前 MP4 哈希和编码证据。V9–V11 为加快局部返修，改用独立脚本与直接复制交付，没有复用最终门禁。机械 mux 报告保留 `visual_approval:false` 并不错误；真正的缺口是最终 export 未再要求与当前 video/asset/config 哈希绑定的视觉审批。V11 的视觉记录也没有沿用完整审核 schema；实际只记录 6 个编码重点帧，并明确没有全片视觉复核。

另一个可确认的问题是元数据漂移：V11 的 `selection.json` 已写用户选 C，却继承候选阶段的 `videoModified:false`；实际 112 张 PNG 已由 mux 报告合入视频。不能用这份选择记录判断“没改片”或“可删补丁”。发布与恢复必须读取实际 mux 报告、输出哈希和采用补丁哈希；后续入口需更新此字段并让视频再改动自动使旧审批失效。这次复盘指出问题，不宣称旧历史元数据都已修改。

关于生图数量，另一会话核算过 35 帧源头部 ROI，得到 24 种字节哈希。压缩噪声和微移也会改变哈希，这不是 24 张独特手绘原画的证明。玩球原片有 13 种姿态、实际按 38 个保持区间安排，说明差分数量与节奏都需要源动作记录；不能用文件哈希去重或固定取模直接判原画数量。

1:24 嘴部返修还暴露了色键挖孔：酒红嘴腔接近背景，被抠为透明露出米白框。只填 alpha 后用户仍不接受头向和嘴形，最终采用完整 C 面板原画。人物内部默认保持实心；背景色相似不是挖掉嘴、眼、皮肤的依据。

## 恢复与清理已经到哪一步

当前最低成本的画面恢复骨架是 V8 完整基线 MP4、V11 的 112 张 C 补丁 `[1930,2042)`、R3 的 77 张互救补丁 `[1631,1708)`，以及哈希清单、编码工具/依赖和原音轨。两套补丁不重叠，不能只保存另一会话的 V11 或本会话的 77 张。保留两张 C 原图、R3 采用原画、提示/选择、语义 owner、运动配置与传递依赖，才能继续修改，而不只是重编码既有画面。

已执行的第一轮清理有独立文件哈希核对：工作区 allocated 约 **35.1 → 12.6 GiB**，减少约 **22.5 GiB**；文件系统 `df` 可用空间实际增加约 **5.96 GiB**，两者不能混写为同一释放量。5669 项删除记录与 4961 个受保护文件的 SHA 保持核对通过；删除前提取了 91 项历史元数据。它是这一轮的结果，不预报后续清理收益。

这次清理保留当前 V9–V11 局部编辑、R3 合成与 MP4 patch 路线，代价是旧 V2–V7 NPZ 冷缓存不再随时可用。V8 的全量 `run()` 也会读取 V7 baseline，不能直接重跑；需要重建历史缓存链。旧 V7/V8 packager 还依赖已移除的冻结 V6 ZIP，不再作为当前恢复/发布入口。保留源码不等于所有旧冷启动、字节相等验证与旧打包命令仍能运行。

最小恢复方法与清理边界见 [恢复与清理](恢复与清理.md)。本轮没有在隔离空目录实际重建整片，不能把依赖存在/哈希通过写成“独立可移植包恢复已通过”。

## 下一次的最小防返工闭环

1. 原片连续动作读完，整数帧合同建立，用户改编与源动作分别标清。
2. 先试持物/转头/遮挡/变装，采用图经人体、画风与接触审查，生成差分和源事件互相覆盖。
3. 语义 owner 与相位直接驱动合成，只重渲依赖变化区间。
4. 最终 MP4 原速、半速、全部变动帧和独立审查有相同输出哈希，问题解决后交付。
5. 交付与采用资产哈希保留，清理先核对闭包，经验只记录有证据的结论。

这些改动是下一项目的可执行起点，不能仅靠这份复盘宣称已经彻底解决所有类型的动画问题。
