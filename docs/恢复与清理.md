# 恢复与清理：保存能用的路线，明确退役的路线

此文记载本项目第一轮清理后的维护边界，不适用于直接复制到其他 PV。当前项目脚本 `tools/pv9_mux.py` 固定了本片的 1920×1080、24fps、3768 帧；它不是这个技能包中的通用渲染器。

## 三种不同的保留目标

| 目标 | 必需保留 | 能否由现有记录宣称已验证 |
| --- | --- | --- |
| 播放/交付最新成片 | 最新 MP4、原片/原音轨与校验清单 | 最新成片已解码和局部实际播放；全片视觉零缺陷未证明 |
| 从采用 PNG 恢复画面 | V8 MP4 基线、112 张 V11 C patch、77 张 R3 patch、工具/运行依赖和每文件哈希 | 补丁/关键输入存在且保护哈希一致；这轮未隔离重建整片 |
| 再修改原画并合成 | 上述资料，加采用原画、逐字提示/参考定位、状态、owner、跟踪/层配置、源片/局部源帧、必要 V8 冻结块及传递依赖 | 当前 V9–V11/R3 依赖保留；不代表全部历史冷启动入口可运行 |

**输出画面恢复**与**从源素材重新合成/重新生图**不同。提示词重跑不保证得到相同像素；已采用 PNG 是重要的保底资源，不能因原图还在就删掉所有补丁。

## 当前最小画面恢复集

- V8 基线：`deliverables/manosaba-full-candidate-v8.mp4`。
- C 补丁：`review/manosaba-v11/patched/f1930.png`–`f2041.png`，区间 `[1930,2042)` 共112张；其中前77张来自1:21 C，后35张来自1:24 C。
- R3 补丁：`review/manosaba-pair-r3/frames/f1631.png`–`f1707.png`，区间 `[1631,1708)` 共77张。
- 当前最新已合片：`deliverables/manosaba-full-v11-pair-r3.mp4`；不能与仅含 C 修订的 `manosaba-full-candidate-v11.mp4` 混用。
- `tools/pv9_mux.py`、运行依赖、实际 mux 报告和输出校验；继续改图还需局部编辑脚本及传递依赖。

上述两个 patch 区间互不重叠。恢复清单需列出源基线 SHA256、每个采用补丁的文件哈希、总帧数、帧率分数、尺寸、音轨载荷哈希和预期区间。不要只记录文件夹名称或 PNG 张数。

本包提供只读纯 Python 标准库的[恢复预检](../skill/pv-replication/scripts/verify_recovery.py)。它读取用户本地清单，核对基线与每张 patch 哈希、整数帧范围、相邻帧空缺和区间冲突，输出计数；不解码/合成，不读取凭证，也不删除文件。它不能证明修复像素、帧率、音轨或实际恢复已成功。

```bash
python3 skill/pv-replication/scripts/verify_recovery.py recovery-manifest.json --root /path/to/project
```

清单格式：

```json
{
  "schema": "pv-minimal-recovery-v1",
  "base": {"path": "deliverables/baseline.mp4", "sha256": "真实64位哈希"},
  "media": {"fps_num": 24, "fps_den": 1, "total_frames": 3768, "width": 1920, "height": 1080},
  "patch_sets": [
    {"id": "C", "interval": [1930,2042], "frames": [
      {"frame": 1930, "path": "review/C/f1930.png", "sha256": "真实64位哈希"}
    ]}
  ]
}
```

示例只展示一帧的字段，完整清单必须列齐整个区间；直接复制应校验失败。`media` 是待后续媒体工具核验的声明，不是此预检已探测的结果。

## 使用已经验证的项目入口恢复

当前安全方法是从 V8 恢复两段 C，再将 R3 合入，不生图、不重做全片图层。实际原脚本使用 OpenCV/NumPy/imageio_ffmpeg，它们是当前项目依赖；纯标准库预检不能取代编码器。

在具有当前工具和依赖的本地工程根运行，输出用新名字：

```bash
.venv/bin/python tools/pv9_mux.py --mode full \
  --input deliverables/manosaba-full-candidate-v8.mp4 \
  --patches review/manosaba-v11/patched --start 1930 --end 2042 \
  --output deliverables/restored-v11-C.mp4 \
  --report review/restored-v11-C-mux.json

.venv/bin/python tools/pv9_mux.py --mode full \
  --input deliverables/restored-v11-C.mp4 \
  --patches review/manosaba-pair-r3/frames --start 1631 --end 1708 \
  --output deliverables/restored-v11-C-r3.mp4 \
  --report review/restored-v11-C-r3-mux.json
```

这是维护方法，**本轮没有执行这两条恢复命令**。它有两次全片编码成本。若后续真正制作通用恢复工具，应接收多个区间，在一次 FFmpeg 原始帧 pipe 中只替换指定帧，然后 copy 原压缩音轨；这样避免重复编码。但新实现必须验证实际媒体参数、PTS、帧数、patch 对位、音轨与区间外画面，不能为“纯 stdlib”去掉这些检查。本轮不新增另一套未验证的合片器。

编码器/依赖不同可能改变输出字节 SHA。恢复后以完整解码、3768帧/24fps/157秒、AAC载荷一致、189张目标对位及边界审核确认语义结果，不许只因文件生成了就写“恢复通过”。不能因为重新编码使其他帧字节变化，就虚称区间外无损；实际已有工具对这两种情形分别记录。

## 原画继续编辑所需依赖

V10/V11 局部编辑读取三个保留的 V8 冻结块 `[1920,1968)`、`[1968,2016)`、`[2016,2064)`及配套指纹 JSON；两张用户选择 C 原图/采用副本、局部源帧、跟踪锚点和旧 body/alpha/layer 的传递依赖也要保留。R3 需要其采用 head/身体/艾玛差分、完整烟团、状态/owner、R2 基础资产与源帧。

不能只把几个入口脚本和 C 图打包就声称“从零可复现”。要可移植，先建立依赖闭包清单，在隔离目录按一条明确路线恢复，并记录版本与实际命令。此 GitHub 工作流包只含方法、代码和空模板，不包含上述原片/角色媒体。

这是这一次清理的实测范围，不预报之后的清理结果。源媒体、角色采用/参考资产、最新 MP4、V8 冻结块、V10/V11/R2/R3必要补丁、当前代码/配置与关键证据仍保留。

旧 V2–V7 NPZ 冷缓存已删除，历史字节相等重放/验证不能直接执行；V8 全量 `run()` 读取 V7 baseline，也需先重建历史链。旧 V7/V8 packager 读取已删除的冻结 V6资源 ZIP，不再充当当前可用打包入口。当前 V9–V11 局部 editor 读取保留 V8块，MP4 patch mux 不读取 raw cache，因而是应优先保留的路线。不能把“保留关键源码”写成“所有旧命令照常可运行”。

以后清理先 dry run，按当前消费者和文件哈希定位重复/可再生项；执行后复核保留闭包。不要通过删除新采用图、源状态记录或仅存的一份 patch换空间。保留淘汰入口说明和当前替代命令，避免下次继续任务误启已经退役的缓存/打包链。
